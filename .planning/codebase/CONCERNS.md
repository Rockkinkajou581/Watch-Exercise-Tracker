# Codebase Concerns

**Analysis Date:** 2026-06-13

## Tech Debt

**Model trained exclusively on synthetic data:**
- Issue: `training/data/readings.csv` and `training/data/sets.csv` were generated by `make_synthetic.py`, not recorded from real wrist motion. Each exercise is a distinct sine wave with unique frequency — trivially separable.
- Files: `training/make_synthetic.py`, `training/data/readings.csv`, `training/data/sets.csv`, `training/artifacts/metrics.txt`
- Impact: The deployed CoreML model (`LiftLoggerClassifier.mlpackage`) was trained on toy data. The perfect 1.0 accuracy/F1 in `metrics.txt` is expected — it does not reflect real-world performance. The model will likely fail on actual recordings.
- Fix approach: Collect real IMU data using the watch app (multiple subjects, multiple sessions), replace synthetic CSVs, re-run `train.py` and `export_coreml.py`, and re-embed the updated `.mlpackage` in Xcode.

**`export_coreml.py` uses deprecated `torch.load` call without `weights_only`:**
- Issue: `torch.load(config.ARTIFACTS / "cnn.pt", map_location="cpu")` omits `weights_only=True`, which is deprecated in recent PyTorch versions and will become an error.
- Files: `training/export_coreml.py` line 31
- Impact: Will produce deprecation warnings now; will break when PyTorch removes the default.
- Fix approach: Change to `torch.load(..., weights_only=True)`.

**`SessionStore.buildMergedExport()` loads all session CSVs into memory as strings:**
- Issue: The entire contents of every readings CSV across all sessions are concatenated into a single in-memory string before writing.
- Files: `LiftLogger/SessionStore.swift` lines 84-121
- Impact: With many long sessions, this can consume significant memory on the iPhone. Readings files grow at 50 Hz × 9 fields; a 30-minute session produces ~90,000 rows.
- Fix approach: Stream-write to the output file row-by-row, or use chunked reads, instead of building a single large string.

**`resendPending()` in `RecorderModel` uses heuristic filename parsing for metadata:**
- Issue: The session ID and file kind are extracted by splitting the filename on `_` and taking `.first` / `.last`, which will produce incorrect results if the session ID format changes or if filenames contain extra underscores.
- Files: `LiftLogger Watch App/RecorderModel.swift` lines 179-186
- Impact: Re-sent files may be filed under the wrong session ID or with the wrong kind on the iPhone side.
- Fix approach: Store metadata in a sidecar file or persist it in `UserDefaults` at session end, rather than re-deriving it from the filename.

**`label_samples()` uses a row-by-row Python loop over set intervals:**
- Issue: In `data.py`, labeling iterates with `for _, row in grp.iterrows()` for each set interval.
- Files: `training/data.py` lines 40-49
- Impact: Scales poorly as the number of sets grows — `O(sessions × sets_per_session × readings)` comparisons. Negligible with synthetic data; noticeable with thousands of real sets.
- Fix approach: Replace with a vectorized merge using `pd.IntervalIndex` or `numpy` broadcasting per `(subject, session)` group.

## Known Bugs

**`scanPending()` lists ALL CSVs in the watch Documents directory, including the active session files:**
- Symptoms: During an active session, `readingsURL` and `setsURL` are in `docsDir`. `scanPending()` runs at session end (via `endSession`) but is also called at init. If the app is force-quit mid-session and relaunched, the active incomplete files appear in `pendingFiles` and the "Resend" button will transfer partial/empty CSVs to the phone.
- Files: `LiftLogger Watch App/RecorderModel.swift` lines 244-250
- Trigger: Force-quit the watch app during an active session, then relaunch.
- Workaround: None currently. The partial file may silently overwrite a valid prior transfer on the phone side because `SessionStore` uses `try? fm.removeItem(at: dest)` before moving.

**`setStartMS` captures `ProcessInfo.systemUptime` on the main thread while sensor timestamps come from `CMDeviceMotion.timestamp` on `workQueue`:**
- Symptoms: `setStartMS` is set in `startSet()` which runs on the main thread, while sensor timestamps (`dm.timestamp`) are captured on `workQueue` during the motion callback. Both use `systemUptime` but there is a small thread-scheduling gap between when the user taps and when `setStartMS` is stored.
- Files: `LiftLogger Watch App/RecorderModel.swift` lines 115-122
- Impact: The set boundary in `sets.csv` may be off by a few milliseconds to tens of milliseconds relative to the corresponding `time_ms` in `readings.csv`. Generally negligible but can affect labeling at set boundaries.

## Security Considerations

**No input validation on subject ID before embedding in CSV rows:**
- Risk: `subject` is sanitized in `RecorderModel.sanitize()` on the watch side, but `SessionStore.sendSubjectToWatch()` sends the raw string without sanitization; only the watch sanitizes on receipt. Additionally, `resendPending()` passes `Self.sanitize(subject)` using the *current* subject at resend time, not the original recording subject.
- Files: `LiftLogger/SessionStore.swift` lines 67-75`, `LiftLogger Watch App/RecorderModel.swift` lines 177-188
- Current mitigation: Watch-side `sanitize()` strips non-alphanumeric characters.
- Recommendations: Sanitize on the phone side before sending. Persist the original subject alongside the session, not re-read from current UI state at resend time.

**Committed binary model weights:**
- Risk: `training/artifacts/cnn.pt` and `training/artifacts/LiftLoggerClassifier.mlpackage/Data/com.apple.CoreML/weights/weight.bin` are binary artifacts committed to the repo. The training `.gitignore` lists `artifacts/` as ignored, but these files exist in the working tree (likely committed before the gitignore was added or via a separate commit path).
- Files: `training/artifacts/cnn.pt`, `training/artifacts/norm.npz`, `training/artifacts/LiftLoggerClassifier.mlpackage/`
- Current mitigation: None.
- Recommendations: Either remove binary artifacts from git history and rely on `train.py` + `export_coreml.py` to regenerate them, or explicitly track them with Git LFS.

## Performance Bottlenecks

**`buildMergedExport()` is synchronous on the main thread:**
- Problem: The merge reads every session CSV file and builds concatenated strings synchronously in the `buildMergedExport()` method, which is called directly from a SwiftUI `Button` action.
- Files: `LiftLogger/SessionStore.swift` lines 84-121, `LiftLogger/LiftLoggerApp.swift` line 63
- Cause: No background dispatch; large exports will freeze the UI.
- Improvement path: Wrap the file I/O in `Task { await MainActor.run { } }` or dispatch to a background queue, updating `status` on the main actor.

**`refresh()` on `SessionStore` runs directory enumeration synchronously and is called on every `onAppear`:**
- Problem: `refresh()` enumerates the sessions directory and all subdirectories synchronously.
- Files: `LiftLogger/SessionStore.swift` lines 52-65, `LiftLogger/LiftLoggerApp.swift` line 79
- Cause: Called from `.onAppear` without background dispatch.
- Improvement path: Dispatch directory listing to a background thread before publishing to `@Published var sessions`.

## Fragile Areas

**WatchConnectivity file transfer: deleted on delivery without confirmation the iPhone processed it:**
- Files: `LiftLogger Watch App/RecorderModel.swift` lines 349-358
- Why fragile: When `didFinish fileTransfer` reports `error == nil`, the watch immediately deletes the local copy with `try? FileManager.default.removeItem`. If the iPhone's `didReceive file` callback fails (e.g. out of storage), the file is permanently lost — there is no retry path and the watch copy is gone.
- Safe modification: Add a confirmed-receipt handshake (e.g. application context message back from phone) before deleting the watch copy, or keep copies for a grace period.
- Test coverage: No tests exist for WatchConnectivity delegate logic.

**`openFiles()` in `RecorderModel` overwrites any existing file for the same session ID:**
- Files: `LiftLogger Watch App/RecorderModel.swift` lines 231-242
- Why fragile: Session IDs are generated from wall-clock time with second precision (`yyyyMMdd-HHmmss`). Starting two sessions within the same second (e.g. during testing) silently overwrites the first session's files before any data is written to them.
- Safe modification: Append a random suffix or check for collision before writing the header.
- Test coverage: None.

**CoreML model version is not checked at runtime:**
- Files: `LiftLogger Watch App/LiftLoggerWatchApp.swift`, `LiftLogger Watch App/RecorderModel.swift`
- Why fragile: The `.mlpackage` is embedded at build time. If the exercise list (`exercises` array in `RecorderModel`) diverges from `classes.json` used to train the model, the app will produce silently incorrect labels with no runtime error.
- Safe modification: At app launch, load `classes.json` from the bundle and assert it matches the `exercises` array, or drive the UI exercise list from the model's metadata rather than a hardcoded Swift array.
- Test coverage: None.

## Scaling Limits

**Single-subject baseline — current split warning is surfaced but not enforced:**
- Current capacity: `make_splits()` warns when fewer than 3 subjects are present and falls back to window-level splitting, producing optimistic accuracy estimates. The codebase has synthetic data for 4 subjects but no mechanism prevents a single-subject real-data run from silently reporting misleading metrics.
- Limit: With 1-2 real subjects, reported test accuracy will not generalize to new users.
- Scaling path: Require >= 3 subjects for a valid evaluation, or explicitly label metrics as "within-subject" vs "cross-subject" in `metrics.txt`.

## Missing Critical Features

**No on-watch inference — the CoreML model is built but never used on the watch:**
- Problem: `export_coreml.py` generates `LiftLoggerClassifier.mlpackage` and describes its usage in a comment, but there is no Swift code in the watch app that loads or calls the model for real-time classification.
- Blocks: The core product feature (automatic exercise recognition) is not implemented. The watch app is currently a data collection tool only.

**No rep counting:**
- Problem: Neither the watch app nor the training pipeline includes rep detection or counting logic.
- Blocks: Users cannot see rep counts during a set; the model classifies exercise type but not reps.

## Test Coverage Gaps

**Zero functional tests exist:**
- What's not tested: All business logic — `RecorderModel` session lifecycle, `SessionStore` file management, CSV merge, WatchConnectivity delegate callbacks, `sanitize()` edge cases, Python data pipeline (windowing, labeling, splitting).
- Files: `LiftLoggerTests/LiftLoggerTests.swift` (empty placeholder), `LiftLoggerUITests/LiftLoggerUITests.swift` (launch only), `LiftLogger Watch AppUITests/` (launch only). No `LiftLogger Watch AppTests/` directory with unit tests.
- Risk: Any regression in file I/O, CSV formatting, or state machine transitions will go undetected.
- Priority: High — the data schema contract between watch CSV output and Python training pipeline is load-bearing and has no automated verification.

**Training pipeline has no tests:**
- What's not tested: `label_samples()` boundary conditions, `make_windows()` purity gate, `make_splits()` group leakage prevention, `compute_norm()` correctness.
- Files: `training/data.py`, `training/features.py`, `training/models.py`
- Risk: Silent data leakage between train/test splits would go undetected, producing misleadingly high accuracy.
- Priority: High.
