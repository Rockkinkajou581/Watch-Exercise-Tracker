Module 1 · The sensor

The tap that starts everything

You strap on the watch, tap Start Session, tap incline chest press, knock out 8 reps, tap End Set. Under the glass, something has been frantically scribbling the whole time.

50 snapshots of your wrist, every second

Inside the watch is an IMU — a chip that measures motion. LiftLogger reads it 50 times per second. Each read is 6 numbers: how hard the wrist is accelerating in 3 directions, and how fast it's rotating in 3 directions. That's your "incline chest press" turned into a stream of numbers a computer can learn from.

acc_x/y/z gyro_x/y/z samples written: 0

The app calls this rate FS = 50 (FS = "frequency of sampling," in hertz). Hold onto that number — in Module 4 you'll see it has to match in two completely different programs, or nothing works.

Why it keeps gravity in the numbers

The watch could subtract out gravity and report only the motion you add. LiftLogger deliberately does the opposite — it adds gravity back in. Gravity always points down, so it secretly tells you which way the arm is tilted. That orientation is a huge clue for telling a shoulder press (arm overhead) apart from a curl (arm down).

// Total acceleration INCLUDING gravity.
// Gravity encodes arm orientation, which
// helps separate exercises.
let ax = dm.userAcceleration.x + dm.gravity.x
let ay = dm.userAcceleration.y + dm.gravity.y
let az = dm.userAcceleration.z + dm.gravity.z
let r  = dm.rotationRate  // rad/s, 3 axes
In plain English

"Acceleration you caused" + "the pull of gravity" = the full picture of where the arm is and how it's moving.

Throwing gravity away would have made two different exercises look identical to the model.

A machine that can only be in one mode at a time

How does the app know that "End Set" means something only if a set is open? It uses a state machine: at any moment the app is in exactly one labeled mode, and only certain moves are legal.

idle → resting → countdown → inSet → enteringReps → (back to resting)

You can't "End Set" from resting, and you can't tap an exercise from idle. Illegal moves are simply impossible — the bug never gets a chance to happen.

Aha — why a vibe coder should care

"Use a state machine" is a phrase you can hand to an AI coding tool. It's the difference between "add a flag to track if we're recording" (which spawns edge-case bugs forever) and a design where bad states cannot exist. When your app has modes — recording/paused, logged-in/out, loading/loaded — name them and make the illegal jumps impossible.

Quick check

Why does LiftLogger keep gravity in its acceleration numbers instead of removing it?

Right idea: gravity is a free orientation sensor. An overhead press and a curl produce different gravity directions, so keeping it makes the two far easier for the model to separate. Speed isn't the reason, and the gyroscope is independent.

Module 2 · The architecture

Meet the cast

LiftLogger isn't one program — it's three, each with one job, passing work down a line like a relay team. Knowing who does what is what lets you tell an AI "put this logic on the watch, not the phone."

⌚️
The Scribe · watchOS

The Watch app

  • The only thing that touches the sensor
  • Writes motion to CSV files
  • Runs the AI live (Modules 5–6)
📱
The Librarian · iOS

The iPhone app

  • Receives files from the watch
  • Files them by date, lets you export
  • Hosts the "rep tagger" (Module 6)
🧠
The Teacher · Python

The training pipeline

  • Runs offline on a laptop
  • Turns CSVs into a trained model
  • Exports a "brain" the watch can run

Notice the one-way street: the watch produces data, the phone stores it, the laptop learns from it — and the learned model gets carried back to the watch. No piece reaches across and pokes at another's internals. That clean separation is why each piece can be rewritten without breaking the others.

The pattern under the hood

Both apps use an observable object: one chunk of state (the "model") that the screen watches. When a number changes — sampleCount, phase — the screen redraws itself automatically. You change the data; the UI follows. That's the whole idea behind SwiftUI, React, and most modern app frameworks.

Quick check

You want to add live "you're going too fast" feedback during a set. Which actor should own that logic?

The Watch. Feedback that must happen in the moment needs the live data, and only the watch has it. The phone only sees files after the fact; the Python trainer runs offline on a laptop and never touches a live session. Matching a feature to the actor that holds the right data is the core architectural instinct.

Module 3 · Data plumbing

Getting the data off the watch

The watch has no keyboard and a tiny battery. So it writes data to plain text files and mails them to the phone — a design that survives a dead app, a dropped connection, even a reboot.

Write a little, write often

Samples arrive 50× a second. Writing each one to disk instantly would be wasteful, so the app collects them in memory (a buffer) and flushes a batch to the file once a second. Crash mid-workout? You lose at most one second.

// workQueue only. Writes buffered lines
// so a crash loses ≤ 1 s of data.
private func flushReadings() {
  guard !lineBuffer.isEmpty,
        let h = readingsHandle else { return }
  let chunk = lineBuffer.joined(separator:"\n")
  lineBuffer.removeAll()      // empty the basket
  try? h.write(contentsOf: chunk.data(...))
}
In plain English

Collect ~50 rows in a basket, dump the whole basket to the file at once, empty the basket, repeat.

Batching like this is everywhere in software: it trades a tiny bit of risk (1 second) for a huge gain in efficiency and battery.

Mailing, not calling

To move files, the watch uses WatchConnectivity's transferFile. This is "mail it and forget it," not a live phone call: the system delivers the file in the background, retrying on its own if the phone is out of range — even if you quit the app. When it arrives, the phone must grab it instantly, because the system deletes the inbox copy the moment the handler returns.

Press play to follow one reading from the sensor all the way to a filed CSV.

The one-clock rule

Here's the subtle masterstroke. Both the motion samples and the "set started / set ended" taps are stamped with the same clock — the watch's time-since-boot clock. That guarantees a reading falls inside a set if its timestamp is between the set's start and end. In Module 4 that single fact is what lets the trainer label the data correctly.

Aha — the clock alignment trick

When two streams of events need to be matched up later, stamp them with the same clock at the source. The phone's "rep tagger" (Module 6) lives on a different device with a different clock — so the watch sends it an "anchor" to translate between the two. Mismatched clocks are one of the sneakiest sources of data bugs.

Quick check

Why must the phone move the received file synchronously the moment it arrives?

Exactly. The delivered file lives in a temporary inbox that vanishes the instant the receive handler finishes. If the phone deferred the move to "later," later would be too late. (And it's not a live call — the watch already mailed it and moved on.)

Module 4 · Machine learning

Teaching the machine

Now there's a pile of CSVs full of numbers. How do they become a model that recognizes "cable curl"? This is supervised learning — learning from examples that already have the right answer attached.

Step 1 — Label every sample

Each row of motion gets tagged with the exercise it belongs to. The trainer looks at the set intervals (start → end) and stamps every reading inside one with that exercise; everything else is rest. It even trims the edges of each set, so the fumbling as you tap the button isn't learned as part of the lift.

# Tag each reading with the exercise of the
# set it falls in, else REST.
for row in sets:
    inside = (t >= row.start_ms) & (t <= row.end_ms)
    labels[inside] = row.exercise

# windows touching a "discard" set are dropped
In plain English

"Every motion reading whose timestamp lands between this set's start and end is this exercise." The one-clock rule from Module 3 is what makes this comparison valid.

Step 2 — Slice into windows

A model can't look at one instant and know the exercise — it needs to see a little movie of motion. So the trainer slides a 2-second window (100 samples) across the stream, stepping halfway each time so windows overlap. A window keeps a label only if 80% of it agrees — straddle a boundary and it's tossed.

2-sec window slides →, 50% overlap window label: —

Step 3 — Split by person, not by window

To know if the model really learned, you test it on data it never trained on. But there's a trap: if your training set and test set share the same person, the model can cheat by memorizing that person's quirks. LiftLogger splits by subject — so the test is always a brand-new body.

Aha — overfitting & honest evaluation

Overfitting is when a model memorizes its study material instead of learning the real pattern — it aces practice and flunks the real test. Splitting by person is like making sure your exam is written by someone whose practice problems you never saw. When an AI tells you "98% accuracy!", your first question should be "accuracy on data it had never seen — including new people?"

The model itself: small on purpose

The brain is a convolutional neural network with only ~150,000 dials (huge models have billions). It's deliberately tiny so it runs instantly on a watch and doesn't overfit a small dataset. It's also "translation-invariant" — it doesn't care where in the window a rep happens, only that the pattern is there.

Quick check

Why does LiftLogger split its data so that no single person appears in both training and testing?

Yes. If the same person is in both sets, the model can score well by recognizing that individual rather than the exercise — an optimistic, misleading number. Holding people out gives you the honest "will this work for someone we've never met?" estimate. The code even prints a warning when there aren't enough subjects to do this.

Module 5 · On-device AI

The brain on your wrist

A trained model on a laptop is useless to a lifter. The last mile is shrinking it into a Core ML file the watch can run live — and that's where some clever engineering hides.

Bake the recipe into the cake

Before training, every number is normalized — rescaled so the model sees tidy values. But the watch only has raw sensor readings. Rather than make the Swift code re-do that math (and risk getting it subtly wrong), the export step bakes the normalization right into the model. The watch hands over raw numbers; the model normalizes them internally and returns probabilities.

def forward(self, x):
    x = x.transpose(1, 2)         # reshape
    x = (x - self.mean) / self.std # normalize
    return torch.softmax(self.model(x), 1)
In plain English

The shipped model carries its own "recipe" (the training mean & std) inside it. Raw sensor data goes in; clean probabilities come out — no chance for the watch and the trainer to disagree on the math.

Predicting, twice a second

Live, the watch keeps a rolling buffer of the last 100 samples and runs the model every 25 new samples — about twice a second. Each run returns a guessed exercise and a confidence (how sure it is, 0–100%).

Press play to watch a guess become a committed decision.
Aha — debouncing

A raw model output flickers frame to frame. Debouncing means: don't act on a change until it's held steady for a beat. It's the same trick behind a light switch that ignores contact bounce, or a search box that waits until you stop typing. Whenever you tell an AI "make this react to live input," ask: should it act instantly, or wait for the signal to settle?

Quick check

The model briefly flashes "shoulder press" for a single frame while you're actually resting. Why doesn't the app log a set?

Correct. A one-frame flicker never survives the "twice in a row" rule, and a low-confidence guess is treated as rest anyway. Together, the confidence threshold and the debounce filter stop noisy single frames from creating phantom sets.

Module 6 · Two algorithms

Counting reps, two ways

The classifier answers which exercise. A different problem is how many reps. LiftLogger solves it two ways — and falls back gracefully from the fancy one to the simple one.

Way 1 — Listen to the rhythm (no labels needed)

A rep is one cycle of a repeating motion. So the simple counter finds the most rhythmic sensor channel, measures how long one cycle takes (its period) using autocorrelation, and divides: reps ≈ total time ÷ time-per-rep. No training data required — it just hears the beat.

wrist motiondetected rep reps: 0

Way 2 — Learn from a human clicking along

The accurate way uses ground truth. While you lift, an observer holds the phone's "rep tagger" and taps once per rep. Those taps (mapped onto the watch's clock via the anchor from Module 3) train a second model that emits one bump per rep. Add the bumps up — that's your rep count.

// Prefer the trained model; fall back to the
// rhythm counter if it isn't bundled yet.
let reps = repModel.count(samples, fs: 50)
        ?? repCounter.count(samples, fs: 50)
In plain English

"Try the smart counter. If it isn't installed, use the simple one instead." The ?? is a fallback: it never crashes for lack of the fancy model — it just degrades to good-enough.

Aha — graceful fallback

Good systems have a plan B that's automatic. The watch tries the trained density model; if that file isn't on the device, it silently uses the rhythm counter. Users never see an error — just a slightly less precise count. "What's the fallback if this isn't available?" is a question worth asking of every feature you build with an AI.

The whole loop, closed

And that's LiftLogger end to end — a system that improves itself: the more you record and tag, the better the next trained model, the better the live detection that collects the next batch.

1 Record on watch 2 Tag reps on phone 3 Train on laptop 4 Bake → Core ML 5 Detect live on watch ↻ repeat
Quick check

The accurate rep-counting model hasn't been added to the watch yet. What happens when you finish a set?

Right. The ?? fallback means a missing model is a non-event: the unsupervised rhythm counter takes over automatically. No crash, no zero — just a slightly less precise count. That's graceful degradation in action.
