The 30-second picture

One loop: motion in, label out

The watch app already does the first box. Everything in the middle — the part that turns recordings into a working model — is what these slides explain.

The goal

What are we actually asking the model to do?

Input: a couple of seconds of wrist motion — six streams of numbers (acceleration in x/y/z, rotation in x/y/z).

Output: one word — bicep_curl, shoulder_press, rest, and so on.

Just classification

Name the exercise. We are not counting reps or scoring form yet — that comes later.

Runs during a workout

The user taps "start," the model watches the motion and names exercises in real time.

Built to grow

Starts with 7 exercises. The design is meant to scale to 20–30 without changes.

Think of it like a language model that, instead of predicting the next word from text, predicts the exercise from a snippet of movement.

The raw materials

The watch hands us two files

① readings.csv — the firehose

One row every 1/50th of a second. Pure numbers, no meaning attached.

# subject, session, time_ms, then 6 sensors
S01,2026..,103.2, 0.04,0.98,0.11, 0.5,-0.2,0.1
S01,2026..,123.4, 0.07,0.95,0.14, 0.6,-0.3,0.2
# ...thousands more...

② sets.csv — the answer key

One row per set you logged on the watch. Short and human.

# subject, session, exercise, start, end
S01,2026..,bicep_curl, 5021.0, 17030.0
S01,2026..,shoulder_press, 21044.0, 33010.0
# ...a handful per session...

readings = "here is the motion."   sets = "...and here's what I was doing, and when." The whole job is to marry the two.

The detail that makes it all work

Both files share one clock

Every timestamp — both the 50-per-second sensor rows and the moments you tapped "start set" / "end set" — comes from the same source: the watch's time since it last booted, in milliseconds.

Because they're measured against the identical clock, a sensor row at time_ms = 6000 can be matched exactly to a set that ran from 5021 to 17030. No guessing, no drift.

If the two files used different clocks (say, one used wall-clock time and one used uptime), they'd be misaligned by seconds and every label would be slightly wrong. The watch code was written specifically to avoid that — and our pipeline relies on it.

From raw files to something a model can learn

Five preparation steps

Raw CSVs can't go straight into a neural network. Our data.py runs this assembly line:

1 · Label

Stamp every sensor row with the exercise happening at that instant — or rest.

2 · Window

Chop the endless stream into bite-sized 2-second clips the model can judge.

3 · Split

Set aside some people entirely for testing, so we measure honest performance.

4 · Normalize

Put all six sensors on a comparable scale so training is stable.

5 · Feed the model  →  covered in the next section

Step 1 · Labeling

Stamp every row with what was happening

We walk through the firehose and, for each row, ask: does its timestamp fall inside one of the logged sets? If yes → that exercise. If it falls in a gap → rest.

"rest" is a real, predictable class. The watch should know when you're between sets, not just guess an exercise non-stop. So idle time becomes its own label.

Step 2 · Windowing

Judge clips, not single instants

A single 1/50th-second snapshot tells you almost nothing. The model needs to see a stretch of motion to recognize the rhythm of a rep.

2-second clips

100 rows each — long enough to contain a rep or two.

50% overlap

We slide forward in ½-sec steps, so we get more examples and never miss a rep that straddles an edge.

Purity gate

If a clip is a messy mix, we drop it unless ≥80% of it agrees on one label.

Step 3 · Splitting — the most important idea here

Test on people the model never saw

⚠ The trap

If I record myself, then randomly scatter my clips into "train" and "test," the model can score 99% — by memorizing my wrist and my watch position. A stranger puts it on → it flops. That false confidence is called data leakage.

✓ The fix

Split by person. All of subject A, B, C → training. Subject D is held out → testing. Now the test score answers the real question: "does this work on someone new?"

With only one subject so far, the code warns you that it can't do this honestly and the score will be optimistic. That nudge is intentional.

Step 4 · Normalization

Put every sensor on the same scale

The six channels live in different ranges — acceleration might swing ±2, rotation ±10. Neural networks train far more smoothly when every input hovers around 0 with a similar spread. So we shift and squeeze each channel to roughly mean 0, spread 1.

The subtle no-cheating rule: we calculate the "shift & squeeze" amounts using only the training data. Peeking at the test data to compute them would leak information and inflate the score — the same leakage sin as before, in disguise.

We save these numbers (norm.npz). They matter again later — the watch will need the exact same shift & squeeze, and we'll bake them right into the shipped model.

Step 5 · The models

We built two — on purpose

The baseline

Random Forest

A simple, fast, hard-to-fool model. Its job is to set the number to beat. If the fancy one can't beat this, the problem is your data — not your model.

The real one

1-D Neural Network (CNN)

The model we actually ship to the watch. More powerful, learns the motion patterns itself, and runs on the watch's tiny chip.

Always build the dumb baseline first. It's your reality check for the whole project.

Model A · the baseline

Random Forest on hand-picked summaries

Instead of feeding raw motion, we compute ~80 summary numbers per clip — the kind of features a human might think of:

How much?
average, min, max, how violently it wiggles (RMS, spread)

How fast?
the dominant rhythm of the rep, via a frequency analysis (FFT)

How linked?
do the axes move together — e.g. twist + lift at once

Those numbers feed a Random Forest — a committee of decision trees that vote on the answer.

  • Fast and robust — trains in seconds, hard to overfit on small data.
  • Tells you which sensors matter — useful for understanding the problem.
  • Catch: to put it on the watch you'd have to re-code all those summaries in Swift — which is why it stays a baseline, not the shipped model.

Model B · the one we ship

The 1-D Convolutional Neural Network

"Convolutional" means it slides small pattern-detectors along the time axis, learning motifs by itself — "a sharp up-twist," "a steady press." Early layers find simple motifs; later layers combine them into "this is a curl."

It ends by averaging each detector across the whole clip (that's the "avg-pool"), then turns those into a label plus a confidence for every exercise.

Why this shape fits the problem

Three reasons the CNN is the right tool

It doesn't care where

A curl is a curl whether it starts at the beginning or middle of the clip. The CNN spots the pattern anywhere along the window. (Jargon: translation invariance.)

It's tiny

~150,000 numbers total. Small enough to run on a watch's chip without draining the battery, yet plenty for this job.

It resists overfitting

That "average everything" final step keeps it from memorizing quirks of your small dataset — it forces it to learn the general shape of each exercise.

This architecture is the long-standing workhorse for "recognize activity from wearable sensors." We're not being exotic — we're using the proven default, which is exactly what you want.

You asked: best vs. worst models

The honest ranking for this problem

USE NOW

  • 1-D CNN — what we ship. Best accuracy-for-effort on a watch.
  • Random Forest — the baseline you must beat. Robust on small data.

LATER, WITH MORE DATA

  • CNN + GRU/LSTM — squeezes out a bit more accuracy; bigger, slower to ship.
  • TCN — handy if some exercises have long, slow reps.

MEDIOCRE HERE

  • Plain MLP on a flattened clip — throws away the time structure.
  • Transformers — data-hungry, heavy; they'd overfit your small set and barely fit on a watch.

AVOID FOR A WATCH

  • k-NN + DTW — must compare against all training data per guess; no clean path onto a watch.
  • Plain RNN — unstable, slow; beaten by the options above.
  • Big pretrained / LLM-style — wildly overkill for six sensor streams.

How training actually runs

Teaching the network, carefully

It repeatedly shows the model clips, lets it guess, and nudges its numbers toward the right answers. Three safeguards make that honest and stable:

Class weighting

rest clips will vastly outnumber any one exercise. Without help the model would just shout "rest." We weight rarer classes more heavily so they get fair attention. (Jargon: class imbalance.)

Early stopping

We watch performance on a held-aside validation set and stop the moment it stops improving — so the model doesn't start memorizing instead of learning.

Save the best

We keep the best version seen during training, not just the last one, and write it to disk along with all the settings needed to reproduce it.

How we judge it

Why accuracy alone lies

Suppose 90% of clips are rest. A lazy model that always says "rest" scores 90% accuracy — and is useless. So we look deeper:

Accuracy

Overall % correct. Easy to read, easy to be fooled by.

Macro-F1

Averages the score per exercise, so a class it always gets wrong can't hide behind the easy majority.

Confusion matrix

A grid of "true vs. guessed." Instantly shows which exercises get mixed up.

Watch the confusion matrix most. When real data arrives, it'll reveal the natural blur — e.g. bicep curl vs. hammer curl move almost identically — and tell you exactly where to collect more examples. All of this lands in metrics.txt.

Getting it onto the watch

Convert to Core ML

The watch can't run Python or our training code. Apple's on-device format is Core ML, so we convert the trained network into a .mlpackage file.

  • We bake the normalization in. Remember the "shift & squeeze" numbers? They're folded inside the model — so the watch just hands over raw sensor values and gets back an answer, no extra bookkeeping.
  • Input: a 100 × 6 block of motion (2 seconds × 6 sensors).
  • Output: a word (classLabel, e.g. "bicep_curl") plus a confidence for every exercise (classLabel_probs).
  • In Xcode you drag the file in, and it auto-writes a Swift class you call like any function.

One model file is the entire deliverable that crosses from "laptop world" into "watch world." Everything before it is just how we earn a good one.

Does it actually run?

Proven end-to-end — on fake data

You haven't collected real recordings yet, so to test the machinery I wrote a generator that fakes the two watch files — each exercise as a distinct fake wiggle. Then I ran the whole pipeline:

python make_synthetic.py   # invent watch files
python baseline_rf.py     # baseline runs ✓
python train.py          # CNN trains, saves ✓
python export_coreml.py   # .mlpackage built & checked ✓
It scored 100%. Ignore that number completely. The fake exercises are trivially different, so a perfect score is expected and means nothing about real performance. What it does prove: every gear turns — loading, labeling, windowing, training, exporting. When real, messy data arrives, the exact same commands work.

Your move

What happens next

  1. 1 · Collect real data. Get the watch app running, then record labeled sets — ideally several people, both wrists, different tempos and weights.
  2. 2 · Export from the phone. Tap "merged export," drop readings.csv + sets.csv into training/data/.
  3. 3 · Run two commands. python train.py then python export_coreml.py.
  4. 4 · Drop the model into Xcode (Watch App target) and call it from the watch.
  5. 5 · Read the confusion matrix in metrics.txt to see which exercises need more data.
