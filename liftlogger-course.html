00 Orientation the idea

What LiftLogger is

A watch that watches you lift: it reads your wrist motion, figures out which exercise you're doing, and counts how many reps, entirely on the device with no internet.

  • The sensor: the watch's 6-axis IMU (accelerometer + gyroscope) sampled at 50 Hz.
  • Job #1, classify: a 1-D CNN names the lift (chest press, curl, row, and so on) from a 2-second window of motion.
  • Job #2, count: a second model counts reps inside each detected set.
  • Two modes: a manual mode for collecting labeled training data, and an AI auto-detect mode that runs the trained models live.
The method behind this course Build first, understand second. The entire app was "vibe-coded": described in plain English, generated by Claude. That gets you a working product fast. This deck is the second half: going back through every file to convert it works into I know why it works.

Why this order works

You learn fastest with a real, working artifact in front of you. Concrete code to read beats abstract tutorials. The risk is shipping things you can't maintain, and the fix is exactly this: a deliberate read-back pass.

00 Orientation the contract

The CSV schemas, and the one clock that ties them together

The whole system is glued by two tiny CSV schemas and a single shared timestamp. Get these right and watch, phone, and Python all agree.

data schemas readings.csv · sets.csv · reps.csv
# readings.csv: one row per IMU sample (50/sec)
subject,session,time_ms,acc_x,acc_y,acc_z,gyro_x,gyro_y,gyro_z

# sets.csv: one row per completed set
subject,session,exercise,start_ms,end_ms,reps

# reps.csv: one row per tagged rep (ground truth)
subject,session,rep_time_ms,set_start_ms,tap_unix_ms
  • subject = who (e.g. S01). session = a timestamp ID. Together they namespace every row.
  • A reading belongs to a set iff start_ms ≤ time_ms ≤ end_ms in the same subject+session. That join is the entire labeling step.
The key decision Every timestamp, both IMU samples and set-boundary taps, uses the watch's time-since-boot clock (CMDeviceMotion.timestamp = ProcessInfo.systemUptime). One clock means samples and boundaries are guaranteed to line up, so labeling is just a numeric comparison.

Why not wall-clock time?

Wall-clock (Date) can jump (NTP sync, timezone, DST). Uptime is monotonic and identical for both the sensor stream and the button taps because they're captured on the same device. The phone's wall-clock taps get converted onto this clock later (slide 16).

  • Why 50 Hz? Lifting motion lives below about 5-10 Hz. 50 Hz gives Nyquist headroom, capturing the shape of every rep without flooding storage. It must match config.FS in Python exactly.

I Capture the 6 channels

What we record, and the gravity decision

Six channels per sample: 3 acceleration + 3 rotation. The subtle, important choice is including gravity in the acceleration.

per-sample channel build
// total accel INCLUDING gravity: gravity encodes
// arm orientation, which helps separate exercises.
let ax = dm.userAcceleration.x + dm.gravity.x
let ay = dm.userAcceleration.y + dm.gravity.y
let az = dm.userAcceleration.z + dm.gravity.z
let r  = dm.rotationRate            // rad/s, gyro

CoreMotion gives userAcceleration (gravity already removed) and gravity separately. Adding them back yields raw total acceleration.

Why add gravity back?The direction of gravity in the watch frame tells you how the arm is oriented. A shoulder press (arm overhead) and a curl (arm down) look very different in the gravity vector even at the same motion, so orientation is useful signal you get for free.

The one rule

Whatever you choose here, be consistent forever: every recording, for both training and inference, must use the identical channel definition and order (acc_x,acc_y,acc_z,gyro_x,gyro_y,gyro_z). The model learns the exact signal you feed it.

I Capture durable I/O

Writing CSV so a crash costs ≤ 1 second

buffer then flush
private var lineBuffer: [String] = []
private let flushEvery = 50          // ~1 s @ 50 Hz

// in the sensor callback:
self.lineBuffer.append(line)
if self.lineBuffer.count >= self.flushEvery {
  self.flushReadings()
}

// flushReadings(): join buffer, one write to FileHandle,
// clear buffer. Runs on workQueue only.
  • Append to a buffer, write in batches. Writing every single sample to disk 50×/sec is wasteful; batching ~1 s of lines into one FileHandle.write is far cheaper.
  • The trade-off is data loss. A bigger buffer means fewer writes but more lost on a crash. 50 lines caps loss at about 1 second, a deliberate balance.
  • Open with headers up front. openFiles() writes the CSV header, then keeps a FileHandle seeked to end for the whole session.
  • End-of-session ordering. The final flush + file transfer is queued behind all writes on the serial queue, so it only runs once every sample is on disk.

I Capture set lifecycle

One set, start to finish, and why each step exists

tap exercise→3·2·1 countdown→inSet (timer)→End Set→enter reps→Save
  • 3·2·1 countdown before the window opens (startSet → beginSetRecording): gives you time to get into position so the front of every set is clean motion, not reaching for a button.
  • Rep entry screen after End Set: you dial in the true rep count (± buttons). This becomes ground-truth in sets.csv.
  • Discard last set: marks a botched set as "discard": its data stays but training drops it (slide 20).
Haptics as a UI languageThe wrist can't be watched mid-lift, so feedback is felt: .click per countdown tick, .start when recording opens, .stop on End Set, .success on save, .failure on cancel/discard. You operate it blind.

Boundary trimming starts here

Because the countdown guarantees a clean start, the Python side sets TRIM_START_SEC = 0 but still trims the end (wind-down before you tap). UI design and data cleaning are co-designed.

II Data flow two-device coordination

The rep-tagger: a live two-device handshake

To train a supervised rep counter you need to know exactly when each rep happened. The approach: a helper holds the phone and taps once per rep while you lift, and the watch tells the phone when to listen.

  • session_start → phone opens reps.csv + stores the clock anchor.
  • set_start → phone "arms" the big TAP button.
  • each tap → one rep timestamp written.
  • set_end → button disarms.
  • session_end → phone closes & files reps.csv.
Channel choiceThis uses sendMessage (not file transfer): it's tiny and live, exactly what real-time coordination needs. It is best-effort, so if the phone app is closed, recording continues fine and you just don't get rep tags that session.

II Data flow cross-device time

Two devices, two clocks, one anchor

The phone tap happens in phone wall-clock time, but the IMU lives in watch uptime. To place a tap on the sensor timeline we convert between them with a single calibration point.

watch captures both clocks together
// at session_start, sent to phone:
"anchorUptimeMs": systemUptime * 1000,   // watch clock
"anchorUnixMs":   Date()...* 1000        // wall clock
phone maps each tap onto the IMU clock
let tapUnixMs = Date()...* 1000
let repTimeMs = anchorUptimeMs
              + (tapUnixMs - anchorUnixMs)
// repTimeMs now matches readings.csv time_ms
The insightCapture both clocks at the same instant once (the anchor). Their difference is the offset between the devices. Add that offset to any later phone timestamp and you've translated it into watch-uptime, the same axis the IMU samples live on.

Why it's "good enough"

It assumes the two clocks tick at the same rate over a short session (true to well under a rep's width). Rep labels only need ~tens-of-ms accuracy, and the density model later smooths each rep with a Gaussian anyway.

III Training config.py

One config file is the single source of truth

Every tunable constant lives in config.py so data, model, export, and the watch all stay in sync. Several of these values are duplicated in Swift and must match.

the knobs that matter

            "gyro_x","gyro_y","gyro_z"]

Coupling alertFS, WINDOW, CHANNELS order, and the reserved labels appear both here and in RecorderModel.swift. Change one, change both, or inference silently breaks. (We return to this "sync tax" on slide 40.)
  • 2-second window ≈ one to two reps, enough motion to recognize the exercise and short enough to react quickly.
  • 50% overlap doubles training windows and means a set boundary never falls between windows.

III Training data.py · label_samples

Step 1: label every sample by interval join

Each reading starts as rest. Then for every set interval, the readings whose time_ms fall inside it get that exercise's label. Pure timestamp arithmetic, which is what the shared clock buys you.

the join + the trim + discard override
labels[:] = REST_LABEL
for row in ordered:            # real sets, then discards
  if row.exercise == DISCARD_LABEL:
    inside = (t >= start) & (t <= end)   # no trim
  else:
    if end-start > trim_total:           # shrink edges
      start, end = start+trimF, end-trimE
    inside = (t >= start) & (t <= end)
  labels[inside] = row.exercise
  • Trim the edges. Button-press setup & wind-down motion at a set's boundaries would teach the model junk, so the interval is shrunk before labeling, and that motion stays rest.
  • Discards win. Bad sets are applied last and override any label, so the next step can drop every window touching them.
  • Keep short sets whole. Trimming is skipped if a set is too short to survive it.
Data cleaning = accuracyHow carefully you define "what counts as the exercise" matters as much as the model. Garbage labels cap your ceiling no matter how good the net is.

III Training data.py · make_windows

Step 2: slice into windows with a purity gate

sliding window + majority label
for start in range(0, len(grp)-W+1, S):
  wl = lab[start:start+W]
  if (wl == DISCARD_LABEL).any():
    continue                  # touches a bad set → drop
  vals, counts = np.unique(wl, return_counts=True)
  j = counts.argmax()
  if counts[j]/W < LABEL_PURITY:
    continue                  # too mixed → drop
  Xs.append(arr[start:start+W]); names.append(vals[j])
  • Windows, not raw samples. The model classifies a 100-sample (2 s) chunk, enough context to see a rep's shape. The label is the majority label in the window.
  • The 80% purity gate throws away windows that straddle a boundary (half rest, half exercise), since they're ambiguous and would confuse training.
  • Windows never cross sessions. Slicing happens inside each (subject, session) group, so a window is always one continuous recording.

III Training the most important slide

Step 3: split by subject, not by window

This single choice decides whether your accuracy number is honest. The question that matters is "how well does it do on a person it has never seen?"

GroupShuffleSplit on subject
if n_subj >= 3:
  groups = ds.groups          # = subject per window
else:
  print("[warn] window split: optimistic")
  groups = np.arange(len(ds.y))
# no subject appears in both train AND test
GroupShuffleSplit(test_size=TEST_FRACTION, …)
   .split(idx, ds.y, groups)
The leakage trapIf you split windows randomly, near-identical windows from the same set land in both train and test. The model "memorizes" that person and reports an inflated accuracy that won't hold up. Grouping by subject prevents this.
  • Cross-subject = the real test. A new user is the biggest source of error in activity recognition.
  • It warns when it can't. With fewer than 3 subjects there's no way to hold one out, so it falls back to window-split and explicitly prints that the numbers are optimistic.

III Training compute_norm

Normalize per-channel, from train only

mean/std over (windows × time)
flat = X.reshape(-1, X.shape[-1])   # (N*W, C)
mean = flat.mean(axis=0)
std  = flat.std(axis=0) + 1e-6      # avoid /0

# IMPORTANT: stats come from the TRAIN split only:
mean, std = compute_norm(ds.X[tr])

Each of the 6 channels gets its own mean & std, then every window is (x - mean) / std. This puts gyro (rad/s) and accel (g) on a comparable scale so neither dominates.

No-leakage ruleStatistics are computed on training data only, then applied to val/test. Computing them over the full dataset would leak test-set information into training, a subtle but real form of cheating.

These stats travel with the model

The exact mean/std are saved to norm.npz and later baked into the Core ML model (slide 34), so the watch feeds raw sensor values and the model normalizes them identically. No risk of a mismatch.

III Training models.py · CNN1D

The model: a compact 1-D CNN

~150k params, ends in global pooling
Conv1d(6→64, k=7) → BN → ReLU → MaxPool
Conv1d(64→128,k=5) → BN → ReLU → MaxPool
Conv1d(128→128,k=3)→ BN → ReLU
AdaptiveAvgPool1d(1)          # collapse time
Flatten → Dropout(0.3) → Linear(128 → n_classes)

Input is (batch, 6 channels, 100 time); output is one logit per exercise class.

  • 1-D convolutions slide along time, learning local motion motifs (the up-down of a rep) regardless of where in the window they start. This is translation invariance.
  • Global average pooling over time means the window length and rep phase don't matter, and it keeps the parameter count tiny (about 150k), which suits a watch.
  • BatchNorm + Dropout stabilize and regularize on a small dataset.
Why small is right hereTiny dataset + tiny compute (Apple Watch Neural Engine) ⇒ a small model that generalizes beats a big one. Capacity you can't feed just overfits.

III Training train.py

The training loop, small but correct

class weights + early stopping on macro-F1
# counter class imbalance (rest dominates)
w = counts.sum() / (counts + 1e-6)
criterion = CrossEntropyLoss(weight = w / w.mean())

# keep the epoch with the best VALIDATION macro-F1
if val_f1 > best_f1:
  best_state = clone(model.state_dict())
if patience >= EARLY_STOP_PATIENCE: break
  • Class weights. rest hugely outnumbers any exercise; weighting the loss by inverse frequency stops the model from just predicting "rest" to win accuracy.
  • Macro-F1, not accuracy, picks the best epoch; it averages per-class, so a rare class can't be ignored.
  • Early stopping restores the best checkpoint when val stops improving, an automatic, leak-free form of regularization.
  • Runs on Apple mps if available, else CPU; drop_last avoids a 1-sample batch breaking BatchNorm.

IV Reps framing

Two different questions, two different models

"Which exercise?" is classification. "How many reps?" is counting a quasi-periodic signal, a different task that deserves its own approach.

Unsupervised · reps.py

Treats a rep as one cycle of a periodic motion. Finds the dominant period by autocorrelation and divides bout length by it. Needs zero labeled rep data to run.

Supervised · density model

Learns from the phone's per-rep taps to emit "one bump per rep." More accurate, especially on wrist-quiet exercises, but it needs the tap ground truth.

Design choiceThe watch ships both, with a graceful fallback: if the supervised model is bundled it's used, otherwise the unsupervised counter runs. You always get a number, and accuracy improves automatically once you've collected tap data and retrained.

Same scoring for both

Both are judged with exact / within-1 / MAE against ground-truth counts, so you can compare them head-to-head and only deploy the supervised one if it actually wins.

IV Reps reps.py · autocorrelation

Unsupervised: find the period, divide

most-periodic channel → dominant lag
for c in range(C):                  # each IMU channel
  x = w[:,c] - w[:,c].mean()
  score, lag = best_autocorr(x, min_lag, max_lag)
  # keep the channel with the strongest periodicity
period = best_lag
autocorr_reps = round(N / period)   # bout / period
# cross-check with a prominence-gated peak count
if peaks ≈ autocorr_reps: return peaks
else: return autocorr_reps
  • Autocorrelation slides the signal against itself; the lag with the highest correlation is the rep period T.
  • Reps ≈ bout length / T. Cross-checked against counting prominent peaks; they agree → trust peaks (better on partial reps), disagree → trust the period.
  • Bounded search: only periods of 0.5-4 s/rep are considered, which removes high-frequency jitter and slow drift.
Classic DSP, no MLA whole feature solved with signal processing and zero training data. The watch runs this identical algorithm live (slide 38), so the Python and Swift versions are kept deliberately in sync.

IV Reps rep_events.py

Supervised data: taps → a density target

The core idea of the supervised counter is the label: instead of a single number, each rep becomes a unit-area Gaussian bump, so the total area under the curve equals the rep count.

resample bout + sum-of-Gaussians
# 1. slice the set's IMU, resample to fixed length
seg = resample(seg, times, REP_BOUT_LEN)   # → 256
# 2. place each rep on the 0..255 grid
rep_idx = (rep_times - t0)/(t1-t0) * (L-1)
# 3. label = sum of unit-area Gaussians (σ = 4)
for r in rep_idx:
  g = exp(-0.5*((grid-r)/sigma)**2); y += g/g.sum()
# area(y) == number of reps  ✓
  • Resample to 256 frames. Bouts of any duration become the same length, so they batch together and the model is duration-agnostic.
  • Unit-area Gaussians mean the target integrates to the count, turning "count" into a smooth regression the network can learn.
  • σ tolerance. The bump's width forgives small timing errors in the human taps (and the clock-anchor conversion).
  • Discards drop out here too, mirroring the classifier.

IV Reps models.py · RepDensityCNN

The rep net: keep time, emit a bump per rep

dilated temporal convnet (TCN)
stem: Conv1d(6→64, k=7)
for d in (1, 2, 4, 8):        # growing dilation
  Conv1d(64→64, k=3, dilation=d) → BN → ReLU → Drop
head: Conv1d(64→1, k=1)
out  = Softplus(head)         # ≥ 0, length L
reps = out.sum()              # integral = count
  • No pooling away of time. Unlike the classifier, the output stays length-256, so it can mark where each rep is.
  • Dilations 1·2·4·8 grow the receptive field to span several reps cheaply, adding context without losing resolution.
  • Softplus forces a non-negative density; the rep count is simply its sum.
  • Trained with MSE against the Gaussian target; scored by exact / within-1 / MAE, per-exercise.

V Deploy models.py · ExportWrapper

Bake normalization into the model

The watch should hand over raw sensor values and get back probabilities, nothing in between. So the export wrapper folds the train-time normalization inside the model.

raw IMU in → softmax out
class ExportWrapper(nn.Module):
  def __init__(self, model, mean, std):
    self.register_buffer("mean", mean)  # frozen stats
    self.register_buffer("std",  std)
  def forward(self, x):       # (B, WINDOW, C) raw
    x = x.transpose(1,2)      # → (B, C, WINDOW)
    x = (x - self.mean)/self.std
    return softmax(self.model(x), dim=1)
  • register_buffer stores the mean/std as part of the model, so they ship inside the .mlpackage and can never drift from what training used.
  • Accepts the natural watch layout (B, WINDOW, C) and transposes internally, so Swift just fills a buffer in sensor order.
  • Softmax inside means the output is ready-to-read probabilities, no post-processing on-device.
Pattern: ship the preprocessingWhenever a model needs preprocessing, baking it into the exported artifact removes an entire class of train/serve-skew bugs.

V Deploy live auto-detect

From predictions to detected sets

A classifier fires ~2×/second on a sliding window. Turning that noisy stream into clean "a set started / a set ended" events needs a small, careful state machine.

  • Sliding window + stride. Keep the last 100 samples; run inference every 25 new samples (inferenceStride) ≈ twice a second.
  • Confidence gate. Below 0.6 top-probability, treat it as rest and never log a shaky guess.
  • Debounce. A label must win commitWindows times in a row before it opens or closes a set, which removes flicker.
  • Min duration. Bouts under 1.5 s are discarded as noise.
  • Lead-in ring. A buffer of recent samples seeds a new bout so its first reps aren't lost while debouncing.
Real-time ML is mostly post-processingThe model is the easy part. Smoothing, thresholding, debouncing, and hysteresis are what make live detection feel solid instead of jittery. These constants are tuned, and live in one place at the top of RecorderModel.

Output stays separate

Auto-detect writes only *_detected.csv (with a confidence column), never readings/sets, so AI-guessed sessions can never be mistaken for hand-labeled training data.

VI Reflection hidden coupling

The "keep-it-in-sync" tax

The most fragile thing in the project isn't any one algorithm. It's that the same constants live in two languages and must agree. The code comments call this out repeatedly for a reason.

The lessonDistributed systems pay a contract tax. The mitigation here is discipline + loud comments. A more robust design would generate the Swift constants from config.py, or have the watch read class names from the model's own metadata instead of a hardcoded array.

VI Reflection tech debt

Where it's still fragile, and that's fine

Knowing your project's weak points is the expertise. None of these are crises; they're a map of what to harden next.

  • Model is synthetic-only. Real data hasn't replaced the sine waves yet, so the headline number is plumbing, not performance.
  • Delete-on-delivery. The watch deletes its copy once a transfer reports success; if the phone then fails to save it, the file is gone. No receipt handshake.
  • scanPending can list an active session's half-written files after a force-quit, risking a partial resend.
  • Merged export is in-memory + on main thread. Large histories could spike memory / freeze the UI.
  • Second-precision session IDs could collide if two sessions start in the same second.
  • Zero functional tests. The critical CSV contract between watch and Python has no automated guard.
It also grew past its own mapThe June codebase audit said "no on-watch inference, no rep counting." The live code now has both, plus the whole supervised rep-tagging system, a reminder that docs date fast, and reading the code is the source of truth.

Systems thinking

The hard parts weren't the neural nets. They were the seams: clocks across devices, schemas across languages, train and serve consistency. The glue is where real systems live or die.

Honest ML

Split by subject, weight imbalanced classes, read macro-F1 and the confusion matrix, and never trust a number whose data you don't understand. Methodology > model.

Deployment is half the project

A trained model is not a feature. Conversion, baked preprocessing, memory layout, and live post-processing are what put it on the wrist.
